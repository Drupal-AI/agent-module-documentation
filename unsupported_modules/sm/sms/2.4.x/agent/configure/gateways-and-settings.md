# SMS Framework — settings, gateways, phone numbers

Admin hub: `/admin/config/smsframework` (route `sms.admin`, permission `administer
smsframework`, which is `restrict access: 1`). All admin routes below require that permission.

## Global settings (`sms.settings`, `/admin/config/smsframework/settings`)

Defaults from `config/install/sms.settings.yml`:

| Key | Default | Meaning |
|---|---|---|
| `fallback_gateway` | `log` | Gateway used when nothing else selects one for a message. |
| `page.verify` | `/verify` | Path of the phone-number verification form. Changing it rebuilds routes. |
| `flood.verify_limit` | `5` | Allowed verification attempts per window. |
| `flood.verify_window` | `21600` (6h) | Flood window in seconds. |

`SmsSettingsForm` validates that the verify path starts with `/`.

## Gateway config entities (`sms_gateway`)

- List/add/edit/delete at `/admin/config/smsframework/gateways`.
- `SmsGateway` config entity; `config_export`: `id`, `label`, `plugin`, `settings`,
  `skip_queue`, `incoming_push_path`, `reports_push_path`, `retention_duration_incoming`,
  `retention_duration_outgoing`.
- `plugin` = an `sms_gateway` plugin id (e.g. `log`, or one from a provider module). `settings`
  is the plugin's own configuration form values. `skip_queue` sends immediately instead of
  queueing. The two `*_push_path` values define the incoming / delivery-report webhook paths
  (must start with `/`). Retention durations control how long `sms` message entities are kept.
- Default install ships one gateway, `log` (`config/install/sms.gateway.log.yml`), plugin `log`.

To add a real gateway, install its provider module (see drupal.org/node/2641028), then create a
gateway instance selecting that plugin and entering the provider's API credentials in the
plugin settings.

## Phone number settings (`phone_number_settings`)

- List/add/edit at `/admin/config/smsframework/phone_number`.
- A `phone_number_settings` config entity binds an **entity type + bundle** (e.g. `user.user`)
  to a telephone field and stores: the phone-number field name, an (optional) automatically
  created field, the verification message (token `[sms_verification_code:code]`-style via the
  message data), verification code lifetime, and whether to purge unverified numbers.
- Adding settings for `user.user` is the typical setup for verifying users' phone numbers; the
  form can auto-create the telephone field.

## Verification page (`/verify`)

- Route `sms.phone.verify` is generated by `RouteSubscriber` from `sms.settings:page.verify`
  (only if the path is ≥2 chars). Permission `sms verify phone number`.
- `VerifyPhoneNumberForm`: user enters the code received by SMS; the form is flood-limited
  (`flood.verify_limit`/`window`), checks the code exists, is unused, and not past its
  configured lifetime, then marks the verification `status = TRUE` and clears the code.
- Codes are generated in `PhoneNumberVerification::newPhoneVerification()` as
  `strtoupper((new Random())->name(6))` and delivered as an outgoing SMS.

## Drush

No module-specific Drush commands. Use `drush config:*` for `sms.settings` / gateway entities.
