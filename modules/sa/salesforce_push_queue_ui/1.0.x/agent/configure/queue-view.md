# Queue screen: the view, the reset routes, and how to drive them

## Install

```bash
composer require drupal/salesforce_push_queue_ui
drush en salesforce_push_queue_ui -y     # pulls in salesforce_push + views
```

`salesforce_push` comes from the `drupal/salesforce` project; without it (and a configured
Salesforce auth provider) the `salesforce_push_queue` table does not exist and the view is empty.

## The shipped view

`config/install/views.view.salesforce_push_queue.yml` — view id `salesforce_push_queue`,
`base_table: salesforce_push_queue`, `base_field: item_id`, page display at
`/admin/content/salesforce-push-queue` (the README's `/admin/config/salesforce/push-queue` is
stale — the routes the module actually generates live under `/admin/content/…`).

Read or edit it as ordinary Views config:

```bash
drush cget views.view.salesforce_push_queue
drush cget views.view.salesforce_push_queue display.default.display_options.fields --format=json
```

**Gotcha:** the exported view lists `view_custom_table` in `dependencies.module`, but that module
is not a declared dependency of `salesforce_push_queue_ui`. Drupal drops config whose dependencies
are unmet, so on a site without `view_custom_table` the view silently fails to install. (Verified
on a site that *does* have `view_custom_table` enabled: the view installs normally.) Verify:

```bash
drush cget views.view.salesforce_push_queue >/dev/null 2>&1 && echo present || echo MISSING
```

If missing, either `drush en view_custom_table -y` and re-import the module's default config
(`drush cim --partial --source=web/modules/contrib/salesforce_push_queue_ui/config/install`), or
build your own view on the `salesforce_push_queue` base table — all the Views data below is
registered regardless of whether the default view exists.

## Reset routes

| Route | Path | Effect |
|---|---|---|
| `salesforce_push_queue_ui.reset_failures` | `/admin/content/salesforce-push-queue/reset-failures/{item_id}` | `failures = 0`, `last_failure_message = NULL`, `updated = time()` |
| `salesforce_push_queue_ui.reset_expiration` | `/admin/content/salesforce-push-queue/reset-expiration/{item_id}` | `expire = 0`, `updated = time()` |

Both: `_permission: 'administer salesforce'`, `_csrf_token: 'TRUE'`, `item_id: \d+`,
`_admin_route: TRUE`. Because of the CSRF requirement the URLs are only usable when generated by
Drupal (`Url::fromRoute()` adds the token) — you cannot hand-craft them.

Generate one in PHP:

```php
$url = \Drupal\Core\Url::fromRoute('salesforce_push_queue_ui.reset_failures', ['item_id' => 42], [
  'query' => ['destination' => '/admin/content/salesforce-push-queue'],
]);
```

## Doing the same thing without the UI

The routes are thin wrappers around one `UPDATE`. From Drush, for scripted recovery:

```bash
# Retry every permanently-failed item for one mapping.
drush sqlq "UPDATE salesforce_push_queue SET failures = 0, last_failure_message = NULL, updated = UNIX_TIMESTAMP() WHERE name = 'my_mapping'"

# Release stale leases so cron can claim the items again.
drush sqlq "UPDATE salesforce_push_queue SET expire = 0, updated = UNIX_TIMESTAMP() WHERE expire < UNIX_TIMESTAMP()"

# What is actually in the queue?
drush sqlq "SELECT name, op, COUNT(*), MAX(failures) FROM salesforce_push_queue GROUP BY name, op"
```

Processing the queue is unchanged — `salesforce_push` drains it on cron
(`drush cron`, or `drush queue:run cron_salesforce_push`).

## Failure-message rewriting

`salesforce_push_queue_ui_views_pre_render()` runs only for `$view->id() === 'salesforce_push_queue'`
and strips these two prefixes from `last_failure_message` before render:

- `Permanently failed queue item %item failed %fail times. Exception while pushing entity %type %id for salesforce mapping %mapping. `
- `Queue item %item failed %fail times. Exception while pushing entity %type %id for salesforce mapping %mapping. `

A custom view with a different id keeps the full raw message.
