# Configure the Menu Block Current Language block

There is no global settings page. You use the module by **placing its block instead of the core menu
block** and, optionally, tuning which link-type providers get filtered.

## Placing the block

Place a block whose plugin id is `menu_block_current_language:<menu_name>` (one derivative per menu,
generated by core's `SystemMenuBlock` deriver) at *Structure → Block layout* (`admin/structure/block`),
or via config/Drush. It appears under the admin category **"Menu block current language"**. It replaces
the equivalent `system_menu_block:<menu_name>` — do not use both for the same menu.

## Block settings

Inherits all core menu-block settings (`level`, `depth`, `expand_all_items`) plus one added setting:

| Setting | Type | Default | Meaning |
|---|---|---|---|
| `translation_providers` | array (checkboxes) | `{views: 'views', menu_link_content: 'menu_link_content', default: 0}` | Which core link-type providers are subject to language filtering. A provider set to `0`/unchecked is **skipped** (its links are never hidden). |

Checkbox options in the block form (`blockForm`):
- `menu_link_content` — filter custom menu links (menu_link_content entities). On by default.
- `views` — filter Views-provided menu links. On by default.
- `default` — string translation for `MenuLinkDefault` titles. **Experimental, off by default.**

Stored in the block config entity under `settings.translation_providers` (schema
`block.settings.menu_block_current_language:*`).

## How filtering works (so you know what to expect)

`MenuBlockCurrentLanguage::build()` loads the tree, then runs core `checkAccess` +
`generateIndexAndSort`, then the module manipulator
`menu_block_current_language_tree_manipulator::filterLanguages` with the `translation_providers` array.
For each link it resolves the provider (`MenuLinkDefault` → `'default'`); if that provider is present and
disabled it is skipped, otherwise `hasTranslation()` is evaluated for the **current content language**:

- `MenuLinkContent` → entity `hasTranslation($langcode)` (non-translatable entities always pass).
- Views menu link → the view's `langcode` config / language config override must exist for the language.
- Title is a `TranslatableMarkup` (`MenuLinkDefault`) → looked up in `locale` string storage (source
  language always passes).
- Implements `MenuLinkTranslatableInterface` → its own `hasTranslation($langcode)`.
- Anything else → visible.

The result is passed through a `HasTranslationEvent`, then links with no translation get
`AccessResult::forbidden()` and disappear from the rendered menu. See [../api/events.md](../api/events.md)
to influence the decision from code.

## Example: place via Drush config (illustrative)

```php
// drush php:eval — place the main menu, filtering menu_link_content only.
$block = \Drupal::entityTypeManager()->getStorage('block')->create([
  'id' => 'mbcl_main',
  'plugin' => 'menu_block_current_language:main',
  'region' => 'primary_menu',
  'theme' => \Drupal::config('system.theme')->get('default'),
  'settings' => [
    'id' => 'menu_block_current_language:main',
    'label' => 'Main navigation',
    'level' => 1, 'depth' => 0, 'expand_all_items' => FALSE,
    'translation_providers' => ['menu_link_content' => 'menu_link_content', 'views' => 0, 'default' => 0],
  ],
])->save();
```
