# Membership — manual setup guide

**Membership** (`membership`) is a framework for modelling **site memberships** as
first‑class content entities, driven by pluggable **membership‑provider** plugins and
integrated with **Commerce** and **State Machine**. It defines a revisionable
`membership` content entity and `membership_type` config bundles, where each type is
bound to a provider plugin that governs the membership's lifecycle. A membership's
status (active, expired, cancelled, and so on) is tracked as a State Machine
workflow, and each membership keeps a revision history.

**Do you need this module?** Probably not, unless your situation matches its specific
purpose — and the project is candid about that. Membership is designed to connect
Drupal to an **external system that owns the membership lifecycle**. If you want to
sell recurring memberships and your payment processor supports tokenization (letting
Drupal manage repeat payments), **Commerce License** is usually the better fit. If
instead your processor handles subscriptions through its **own** mechanism — common
with high‑risk‑space gateways, or platforms like Google Play and the iTunes/App
Store — and you mainly need Drupal to **react to that external system's actions**,
then Membership is the right tool. It does **not** process payments itself; it
delegates that to Commerce.

The module ships a bundled **`ManualOnsite`** provider for simple on‑site
memberships, and you add integrations with external systems by implementing the
provider interfaces (which declare capabilities such as "supports creation" or
"supports cancellation"). It has hard dependencies on **State Machine**, the
**Entity API** module, and **Commerce**, and works on Drupal 9 and 10. Access
permissions are the per‑bundle CRUD permissions generated by the Entity API module —
there are no permissions unique to this module.

This guide is written for a **human** clicking through the admin UI. If you want
terse, token‑cheap references for an AI coding agent, read the sibling
[`agent/`](../agent/start.md) docs instead.

There is **no single module settings page**. You work with **membership types** and
**memberships** as entities (and add provider plugins in code), described in "How to
use it" below.

## Where it lives in the admin menu

Membership works through Drupal's entity administration rather than one settings
form:

- **Membership types** (`membership_type` bundles) are managed under **Structure**,
  where each type is bound to a provider plugin and its configurable settings.
- **Memberships** themselves are created and listed as content entities; the add page
  shows only the membership types you can actually create (based on the provider's
  capabilities and your Entity‑API permissions), and can redirect you to a provider's
  off‑site creation page when required. Memberships are also exposed to **Views**.

## How to use it

1. Decide whether Membership is actually the right module for your case (see the note
   above — Commerce License is often the better choice).
2. Create one or more **membership types** under **Structure**, each bound to a
   provider — start with the bundled **Manual (on‑site)** provider for memberships you
   manage directly in Drupal.
3. For an external subscription system, add a **custom provider plugin** (implementing
   the provider interfaces) so memberships are created/cancelled in step with that
   system; Drupal reacts to its actions rather than owning billing.
4. Grant the appropriate **per‑bundle CRUD permissions** (generated by the Entity API
   module) to the relevant roles at **People → Permissions**.
5. Create and manage **memberships** as content entities, tracking their status
   through the State Machine workflow, and surface them in Views as needed.
