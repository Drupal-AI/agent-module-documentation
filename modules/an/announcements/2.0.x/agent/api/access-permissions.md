# Access, permissions & visibility conditions

## Permissions
Static permissions (`announcements.permissions.yml`):
- `administer announcements` / `administer announcements_announcement` (restricted),
- `access announcements_announcement overview`,
- `add`, `edit`, `delete announcements_announcement entities`,
- `view published` / `view unpublished announcements_announcement entities`,
- `view all` / `revert all` / `delete all announcements_announcement revisions`.

Dynamic per-bundle permissions (`permission_callbacks` →
`AnnouncementPermissions::generatePermissions`, `src/AnnouncementPermissions.php`): for each Announcement Type
it builds `create $type`, `edit own $type`, `edit $type any`, `delete $type own`, `delete $type any`,
and `view/revert/delete $type … revisions`.

## Access control handler (`src/AnnouncementAccessControlHandler.php`)
`checkAccess()` per operation:
- **update** / **delete** — allowed if `checkOwn()` matches (owner + a `%bundle edit/delete own` permission),
  else `edit/delete announcements_announcement entities`.
- **view** — unpublished entities require `view unpublished …` (or an owner "view own unpublished"); published
  entities require `view published announcements_announcement entities`, then AND-ed with the entity's
  visibility conditions when present.
- **create** — `checkCreateAccess()` → `add announcements_announcement entities`.

`checkOwn()` only grants "own" access to an **authenticated** account whose id equals the entity owner, so an
announcement left owned by anonymous (uid 0, the `preSave` fallback) does not grant anonymous visitors any
"own" rights.

### Visibility-condition evaluation
`resolveConditions()` (uses `ConditionAccessResolverTrait`) instantiates each condition plugin, applies its
runtime contexts via `context.repository` + `context.handler`, and evaluates with AND logic. A
`MissingValueContextException` forbids access; a `ContextException` forbids only for non-negated conditions.
Cache contexts/tags/max-age from each condition are merged into the result, and the entity itself is added as
a cacheable dependency. This mirrors core Block visibility handling (the reason strings even say "block
visibility condition").

## Routes & their permissions
- `announcements.structure` (`announcements.routing.yml`) — `/admin/structure/announcements`, perm
  `access administration pages`.
- Entity CRUD routes are generated by `AnnouncementHtmlRouteProvider` (extends `AdminHtmlRouteProvider`) and
  gated by the access handler above.
- `RouteSubscriber::alterRoutes()` (`src/Routing/RouteSubscriber.php`, tagged `event_subscriber` in
  `announcements.services.yml`) overrides the entity collection route to require
  `access announcements_announcement overview`.
- Revision routes (`AnnouncementHtmlRouteProvider`) — `version_history`/`revision` require
  `view all announcement revisions`; `revision_revert`/`translation_revert` require
  `revert all announcement revisions`; `revision_delete` requires `delete all announcement revisions`; the
  settings route requires the entity's admin permission. These permission strings differ from the ones
  declared in `permissions.yml` (which use the `announcements_announcement` infix), so the routes are
  effectively restricted to users granted those exact (non-declared) strings — i.e. they fail closed. The
  revision UI/forms live in `src/Controller/AnnouncementController.php` and `src/Form/AnnouncementRevision*`.

## Settings form
`src/Form/AnnouncementSettingsForm.php` is a placeholder `FormBase` (renders static markup, empty
`submitForm()`) mounted at `/admin/structure/announcements/announcements_announcement/settings`. It is
Field-UI's base route for adding fields to bundles, not a real config store; `data.json.configure` is null.

## Rendering & output safety
Announcement `body` renders through a text format; the revision-overview log message is filtered with
`Xss::getHtmlTagList()`. `AnnouncementStorage` uses parameterized queries only. The module makes no outbound
HTTP requests.
