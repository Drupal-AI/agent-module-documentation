# The flag field and the library view

Everything this module does is config plus install glue. Source of truth: `config/install/*`,
`block_component_library.install`, `block_component_library.links.action.yml`, `.module`.

## Install / enable

`drush en block_component_library -y` (or via UI). Dependencies `block`, `block_content`,
`views`, `views_bulk_operations` must be present. On enable, Drupal imports the three
`config/install/` objects, then `block_component_library_install()` runs.

## The field: `field_in_block_component_library`

- **Storage** — `field.storage.block_content.field_in_block_component_library.yml`:
  entity type `block_content`, type `boolean`, `cardinality: 99` (multi-value storage,
  though used as a single flag), `translatable: true`, owner module
  `block_component_library`.
- **Instance (basic bundle)** — `field.field.block_content.basic.field_in_block_component_library.yml`:
  label *"Add to Block Component Library"*, boolean on/off labels `Yes`/`No`, default `0`,
  not required. Description explains it flags the block as a reusable component.
- **Spread to all bundles** — `hook_install()` (`.install`) sets the field on the `basic`
  bundle's form display as a `boolean_checkbox` (weight 99), then loops every
  `block_content` bundle and calls
  `_block_component_library_add_field_in_block_component_library_to_block_content_bundle()`,
  which clones the `basic` `FieldConfig` (label, description, required, translatable,
  default, settings) onto each bundle and adds the same checkbox widget. Bundles created
  **after** install do not get the field automatically — reinstall or re-run the helper.

## The view: `block_component_library`

`config/install/views.view.block_component_library.yml`. Base table
`block_content_field_data`. Two displays:

- **default (master)** — `access: perm` with `perm: 'administer blocks'`; cache `tag`;
  full pager (50/page); table style; VBO bulk form plus columns
  `status`, `id`, `info` (Block description, links to entity), `type`, `langcode`,
  `changed`, `operations`.
- **admin_content_page** — path **`admin/content/block-content-component-library`**, normal
  menu link under `system.admin_content` (Content), title/description "Block Component
  Library" / "Find and manage reusable custom content blocks marked as block component
  library items.".

**Filters** (which blocks appear): `field_in_block_component_library_value = 1` (the flag)
AND `reusable = 1` (core reusable blocks only), both non-exposed; plus exposed filters for
`status`, `info` (contains), `type` (bundle in), and `langcode`.

**Bulk actions** (VBO `selected_actions`): `pathauto_update_alias`, `views_bulk_edit`,
`views_bulk_operations_delete_entity`, `entity:publish_action:block_content`,
`entity:unpublish_action:block_content`, `entity:save_action:block_content`. Pathauto and
views_bulk_edit actions only apply if those modules are installed.

## Access & routing

No module-defined routing/permissions files. The only access control is the view's
`administer blocks` permission on both displays; the menu route is generated by Views.
The "Add custom block" local action reuses core `block_content.add_page`.

## Uninstall

`hook_uninstall()` → `_block_component_library_remove_field_in_block_component_library()`
deletes the field **storage** (removing the field from all bundles) and
`_block_component_library_remove_block_component_library_view()` deletes
`views.view.block_component_library`. No residual config.

## Operating notes

- To include a custom block in the library, edit the block and tick *"Add to Block
  Component Library"* (the block must also be reusable — the default for custom blocks).
- The listing is admin-only (`administer blocks`); it is not a public/anonymous route.
- `cardinality: 99` on the storage is unusual for a flag but harmless; the widget is a
  single checkbox and the view filters on `value = 1`.
