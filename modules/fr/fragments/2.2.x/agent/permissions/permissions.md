# Permissions & access control

Two sources: static permissions in `fragments.permissions.yml`, and dynamic per-fragment-type
permissions generated by `Drupal\fragments\Permissions\FragmentPermissions` (wired via
`permission_callbacks`). Access on individual fragments is decided by
`Drupal\fragments\FragmentAccessControlHandler`.

## Static permissions

| Permission | Flags | Grants |
|---|---|---|
| `access fragments overview` | `restrict access: true` | See the fragments listing at `/admin/content/fragments` (also the access check on the optional VBO view). |
| `administer fragment types` | `restrict access: true` | Create/edit/delete fragment types and their fields (`administer fragment types` is the `fragment_type` admin permission). |
| `administer fragment entities` | `restrict access: true` | The `fragment` entity `admin_permission` — full view/create/update/delete on **all** fragments of every type. |

## Dynamic per-type permissions

For every fragment type, `FragmentPermissions::buildPermissions()` produces six permissions. The
machine name is built by `FragmentPermissions::buildPermissionId($type, $op)` which returns
`"$op $type fragments"` — e.g. for a type `tip`: `create tip fragments`, `view tip fragments`,
`update tip fragments`, `update own tip fragments`, `delete tip fragments`, `delete own tip fragments`.

| Op string | Title | Flags |
|---|---|---|
| `create {type} fragments` | Create %type fragments | `restrict access: true` |
| `view {type} fragments` | View %type fragments | (no restrict flag — safe to give anonymous/authenticated) |
| `update {type} fragments` | Edit any %type fragment | `restrict access: true` |
| `update own {type} fragments` | Edit own %type fragments | `restrict access: true` |
| `delete {type} fragments` | Delete any %type fragment | `restrict access: true` |
| `delete own {type} fragments` | Delete own %type fragment | `restrict access: true` |

Per the README, if you want anyone but administrators to see fragments you **must** grant the per-type
`view {type} fragments` permission — commonly to both anonymous and authenticated roles.

## Access-handler logic (`FragmentAccessControlHandler::checkAccess`)

Let `admin = administer fragment entities` and `owner = fragment.user_id == account.id()`.

- **view**: `admin` OR (`fragment.isPublished()` AND `view {type} fragments`) OR the `view individual`
  result below. Unpublished fragments are therefore visible only to users who can update/delete them
  (or admins).
- **view individual** (custom operation, used only by the canonical `/fragment/{fragment}` route):
  `admin` OR update-access OR delete-access. This is what keeps regular "view" users off a fragment's
  own page while still letting it render when embedded in another entity.
- **update**: `admin` OR `update {type} fragments` OR (`update own {type} fragments` AND `owner`).
- **delete**: `admin` OR `delete {type} fragments` OR (`delete own {type} fragments` AND `owner`).
- **create** (`checkCreateAccess`): `admin` OR `create {type} fragments`.

Access results are cached per-permission (and per-user for update/delete) with the fragment added as a
cacheable dependency, so grants recompute correctly when a fragment changes.

## Grant / check examples

```php
// Programmatic checks.
$mayEditAll = \Drupal::currentUser()->hasPermission('update tip fragments');
$mayView    = $fragment->access('view');            // entity-level, uses the handler above
$mayCreate  = \Drupal::entityTypeManager()
  ->getAccessControlHandler('fragment')
  ->createAccess('tip');
```

```bash
# Drush: let anonymous + authenticated view 'tip' fragments; give editors full control of them.
drush role:perm:add anonymous 'view tip fragments'
drush role:perm:add authenticated 'view tip fragments'
drush role:perm:add editor 'create tip fragments'
drush role:perm:add editor 'update tip fragments'
drush role:perm:add editor 'delete tip fragments'
```

> Note: the revision routes reference `access fragment revisions`, `revert all fragment revisions` and
> `delete all fragment revisions`, which the module never declares — so those permissions cannot be
> assigned to any role and the revision UI is reachable only by the superuser. See
> [../api/entity-api.md](../api/entity-api.md).
