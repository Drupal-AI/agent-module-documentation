# Access model

## What the module contributes

Group Storage adds no custom entity-access code. It relies on the standard Group 3.x mechanism: the
relation is declared `entity_access: TRUE`, so Group generates per-relation group permissions
(view / view unpublished / update / delete, in "own"/"any" scopes) and its own `hook_entity_access`
grants access to a `storage` entity when the acting user's group role holds the matching group
permission on the group that owns it. Group Storage's own `GroupStoragePermissionProvider` only
remaps one legacy permission name (`view unpublished … any`); it does not change how access is
decided.

Configure the group permissions per group type at
`/admin/group/types/manage/{group_type}/permissions`.

## Permissions

- **Module-provided group permission:** `access group_storage overview` — gates the per-group
  overview view and the "Storages" operation link. Overview-list access only; it is **not** an
  item-level view grant.
- **Per-relation group permissions:** generated by Group for each `group_storage:<type>` relation
  (create/view/update/delete relationship and, via `entity_access`, the target-entity operations).

## The overview view

`view.group_storages` (`page_1` at `group/%group/storages`) uses the `group_permission` access
plugin (`access group_storage overview`) and a `group_id` argument with `default_action:
access denied`, so it always requires a group context and that permission. Its default page display
filters to **published** storage. The rows are produced through a group-relationship reverse
relationship, so the list is correctly **scoped to one group** — there is no cross-group listing.

## Interplay to understand (not a module bug)

Storage entities also have their **own** access handler
(`Drupal\storage\StorageAccessControlHandler`) driven by **site-wide** permissions such as
`view published storage entities`, `view published <bundle> storage entities`,
`edit storage entities`, `delete storage entities`, and `administer storage entities`, plus a
canonical route `/storage/{storage}`. Drupal combines access results such that **any** ALLOWED wins
(only FORBIDDEN overrides). Group's `entity_access` integration only ever **grants** access via
group permissions — it never returns FORBIDDEN. Therefore group scoping is only effective if those
Storage site-wide view/edit/delete permissions are **not** granted broadly. If, say, authenticated
users hold `view published storage entities` site-wide, any authenticated user can read any group's
storage at `/storage/{id}` regardless of group membership. This is inherent Group behaviour, not a
defect in group_storage, but it is the single most important thing to get right when relying on this
module for confidentiality.
