# Admin, routes & permissions

## Install / enable

```
composer require drupal/api_token_entity:^1.0
drush en api_token_entity -y
```

Requires Drupal `^11.3`, PHP 8.4+ (the code uses PHP 8.4 `new Expr()->method()` syntax, e.g. `new DrupalDateTime('now')->getTimestamp()`), and core `datetime` (declared dependency). No config to import — the entity types carry their own base-field schema; there is no `config/install`, `config/schema`, or `.install` file, and no Drush commands.

## Permissions

`api_token_entity.permissions.yml` defines one permission:

- **`administer api_token_entity entities`** — `restrict access: true`. Grants full create/view/edit/delete on both entity types.

Enforcement: `ApiTokenEntityAccessControlHandler` (`src/ApiTokenEntityAccessControlHandler.php`) returns `AccessResult::allowed()` for `checkAccess()`/`checkCreateAccess()` only when the account holds that permission, else `AccessResult::neutral()`. Both entity types also set `admin_permission` and `collection_permission` to the same permission in their attribute. There is no per-owner scoping — tokens are global admin-managed objects, not user-owned.

## Routes & menu

Entity CRUD routes are generated by the core `AdminHtmlRouteProvider` under:

- Tokens: `/admin/config/services/api-token-entity/api-token/{list,add,{id}/edit,{id}/delete,delete}` — collection route id `entity.api_token_entity_api_token.collection`.
- Types: `/admin/config/services/api-token-entity/api-token-type/{list,add,{id}/edit,{id}/delete,delete}` — collection route id `entity.api_token_entity_api_token_type.collection`.

`api_token_entity.routing.yml` adds one landing route, `api_token_entity.admin_config_services_apitoken` at `/admin/config/services/api-token-entity`, rendering the core system admin-menu block. Menu links (`api_token_entity.links.menu.yml`) place "API token entity" under *Configuration › Web services*, with "API tokens" and "API token types" children pointing at the two collection routes.

Operational note: the landing route's requirement is `_permission: 'access api_token_entity pages'`, but that permission is **not** defined by the module — so the landing page itself is only reachable by user 1 (an undefined permission is never granted). The two entity collection pages are reachable directly by any holder of `administer api_token_entity entities` via their own routes/menu links, so this does not block token administration; navigate to `…/api-token/list` and `…/api-token-type/list` directly if the parent page 403s.

## Operating

1. Create one or more **API token types** (e.g. `read_only`) — the `name` must match `^[a-z0-9_.]+$`.
2. Create an **API token**: pick a type, set a Consumer ID (`name`), keep or adjust the auto-generated value and the `+1 year` expiration. **Copy the value immediately** — only the hash is stored afterwards.
3. **Rotate** a token from its edit form (issues a new value shown once); **delete** to revoke.
4. Use the **Validate Token** form embedded on the token list page (`ApiTokenCheckerForm`) to confirm a given string/type is currently accepted; it reports the matching Consumer ID or "not valid".

## Services

`api_token_entity.services.yml` registers: the `api_token_entity.access` logger channel, the `api_token_entity.api_token.manager` (`ApiTokenManager`), and the `access_check.api_token_entity.api_token_type` access checker (tagged `access_check`, `applies_to: _api_token_type`). See [validation](../api/validation.md).
