FillPDF fills the fields of an uploaded PDF template (AcroForm) with data from Drupal entities (nodes, users, webform submissions, etc.), replacing values via tokens, then downloads, saves, or redirects to the generated PDF. Filling is delegated to a pluggable backend: the hosted FillPDF Service, a self-hosted FillPDF LocalServer, or locally installed pdftk.

---

An admin uploads a PDF template (`.pdf` only) to create a **FillPdfForm** content entity; FillPDF parses
its fillable fields into **FillPdfFormField** entities. For each field you map a token/value (text) or an
image field. PDFs are generated by visiting `/fillpdf?fid=<id>&entity_id=<type>:<id>` (route
`fillpdf.populate_pdf`), which is access-checked by `FillPdfAccessController::checkLink()` →
`FillPdfAccessHelper`: administrators and users with *publish all pdfs* always pass; users with *publish
own pdfs* pass only if they can `view` every entity in the request context; everyone else is forbidden.
`HandlePdfController::populatePdf()` parses the request (`FillPdfLinkManipulator`), loads entities,
merges via the configured **PdfBackend** plugin (`fillpdf_service`, `local_server`, or `pdftk`; managed by
`plugin.manager.fillpdf.pdf_backend`) through a `BackendProxy`, builds a token-replaced, sanitized
filename, and dispatches a **FillPdfActionPlugin** (`download`, `save`, or `redirect`; managed by
`plugin.manager.fillpdf_action.processor`). Storage scheme handling is careful: a form's target scheme
must be both available and in `allowed_schemes` (default `[private]`) or the file is only streamed to the
browser. The pdftk backend builds XFDF and calls pdftk via `exec()`/`passthru()` with shell-escaped
arguments (template path, owner/user passwords), and supports PDFtk encryption strength and permission
flags per form. The FillPDF Service backend talks XML-RPC to a remote endpoint (HTTPS by default) with an
API key and anonymizes image filenames; LocalServer posts base64 JSON to a self-hosted HTTP API. Config
lives in `fillpdf.settings` (`admin/config/media/fillpdf`); templates and forms are managed at
`admin/structure/fillpdf`. Depends on core `file`, `options`, `serialization`, `views`, and contrib
`token`. Hooks: `hook_fillpdf_form_form_pre_form_build_alter`, `hook_fillpdf_populate_pdf_context_alter`.

---

- Generate a filled-in PDF (e.g. a contract, application, or certificate) from a node's field data.
- Populate a government/registration form template from a user profile.
- Turn a webform submission into a completed PDF document.
- Map PDF AcroForm fields to Drupal tokens like `[node:title]` or `[webform_submission:values:name]`.
- Place an uploaded image (signature, logo, photo) into an image field of the PDF.
- Offer a "Download as PDF" link on a content page that merges the current entity.
- Save generated PDFs to private file storage for later retrieval instead of only downloading.
- Redirect the visitor straight to the saved PDF after generation.
- Restrict PDF generation so users can only produce PDFs from content they may view (*publish own pdfs*).
- Let trusted roles generate PDFs from any content (*publish all pdfs*).
- Batch-fill a single template with different entities by changing the `entity_id` in the link.
- Produce a sample/blank PDF from a template for admins (`sample=1`).
- Flatten generated PDFs so form fields become static (default), or keep them fillable (`flatten=0`).
- Force a download rather than inline display via `download=1`.
- Name output files from tokens (e.g. `Invoice-[node:title].pdf`) with automatic sanitization.
- Encrypt output PDFs (40/128-bit) and set owner/user passwords and permission flags via pdftk.
- Use the hosted FillPDF Service so no server-side binary is required.
- Self-host PDF processing with FillPDF LocalServer (Docker) for data-privacy control.
- Use locally installed pdftk on a VPS/dedicated server for fully on-server processing.
- Transform values before writing them into the PDF (per-form replacements/mappings).
- Store filled-PDF metadata (which context produced a file) via FillPdfFileContext.
- Import/export a FillPDF form's configuration and field mappings between sites.
- Duplicate an existing FillPDF form and its mappings to start a new one quickly.
- Choose per-site allowed storage schemes and a template storage scheme (private recommended).
- Alter the merge context in code (e.g. auto-attach a user's latest webform submission) via a hook.
