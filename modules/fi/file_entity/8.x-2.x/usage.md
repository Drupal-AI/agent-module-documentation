File entity turns Drupal's core file into a first-class fieldable entity: files gain **types** (bundles), can carry **fields**, are **viewable** with display modes and field formatters, and are exposed to Views, Token and the Entity API.

---

Out of the box a Drupal file is a thin record — a URI and some metadata. File entity extends it so files behave like nodes: you define **file types** (bundles), typically by MIME (image, document, video, audio), attach **fields** to each type (captions, credits, rights, alt metadata), and give files **view displays** so a file has its own page (`/file/{file}`) and can be rendered with field formatters. It adds a file administration listing (`/admin/content/files`), a type UI (`/admin/structure/file-types`), an add/upload flow, inline edit, download and delete routes, and archive/bulk-delete tooling, plus Views and Token integration for listing and templating files.

Access is enforced through a full permission set: `administer files`, `administer file types`, `create files`, `view files`, `view own files`, `view private files`, `view own private files`, and a `bypass file access` escape hatch (all the administrative ones are `restrict access: true`), complemented by per-type permissions generated by a permission callback. The entity routes are gated by entity access (`file.view`, `file.download`, `file.update`, `file.delete`) or the matching permission — the two `access content` wizard routes resolve to empty controller stubs, so they perform no action. It is the long-standing successor to the D7 "fieldable files" pattern and integrates with the media ecosystem.

For sites that need rich file metadata, per-type file handling, dedicated file pages, or file listings in Views, it is the canonical way to make files fieldable. Setup is: enable it (pulls in `file`, `text`, `views`, `image`, `token`), define file types and their fields, configure display modes, and grant the file permissions to the appropriate roles.
