# RedHen access model (3.0.x)

RedHen access is **permission-based and active/inactive-aware**, enforced by per-entity
`EntityAccessControlHandler` subclasses. There is no anonymous access by default: every view/edit/
delete decision requires an explicit RedHen permission.

## Base module permissions (`redhen`)

- `administer redhen` — admin tasks.
- `access redhen` — reach the `/redhen` dashboard.

## Contact permissions (`redhen_contact`)

Static: `add contact entities`, `access contact overview` (list page, `restrict access: true`),
`administer contact entities` (the entity `admin_permission`), `delete contact entities`,
`edit contact entities`, `link contact entities to users`, `view active contact entities`,
`view inactive contact entities`. Per-bundle (generated by `ContactPermissions`): `add`,
`view active`, `view inactive`, `view own`, `edit own`, `edit any`, `delete own`, `delete any`
`<bundle> contact`.

`ContactAccessControlHandler::checkAccess`:
- **view / view label**: active contact → `view active contact entities` OR
  `view active <bundle> contact` OR (own only) `view own <bundle> contact`; inactive contact →
  `view inactive contact entities` OR `view inactive <bundle> contact`.
- **update**: own+active may use `edit own <bundle> contact`; otherwise needs `edit contact entities`
  or `edit any <bundle> contact`.
- **delete**: symmetric to update with the delete permissions.
- "own" = `getOwnerId()` (linked `uid`) equals the current user.
- The **"Linked user" (`uid`) form field is hidden** unless the user has
  `link contact entities to users` (`ContactForm::buildForm`).

## Org permissions (`redhen_org`)

`access org overview`, `add org entities`, `administer org entities`, `delete org entities`,
`edit org entities`, `view active org entities`, `view inactive org entities`, plus per-bundle
`add` / `view active` / `view inactive` / `edit` / `delete` `<bundle> org`. Same active/inactive
split for view; no "own" concept (Org has no owner-based branch).

## Connection permissions (`redhen_connection`)

`access the connections overview`, `add connection entities`, `administer connection entities`,
`delete connection entities`, `edit connection entities`, `view active connection entities`,
`view inactive connection entities`, `administer connection role entities`,
`view connection role entities`, plus per-bundle add/view-active/view-inactive/edit/delete. The
collection route requires `view active connection entities+view inactive connection entities` (both).
The per-entity **"Connections" tab** (`RedhenConnections::access`) grants when the viewer has
`view active connection entities` (or, for their own linked entity, `view own active <type>
connection`).

## Connection-Role delegation (opt-in, grant-only) — design carefully

`redhen_connection.module` implements `hook_entity_access` and `hook_entity_create_access`. For a
subject entity, it iterates `ConnectionPermission` plugins (plugin type provided by this submodule:
`ConnectionConnectionPermission`, `OrgConnectionPermission`, `SecondaryContactConnectionPermission`),
loads the current user's Contact (`Contact::loadByUser`), and if that Contact is connected to the
subject under a **Connection Role whose `permissions` list includes the requested operation**, it
returns **Allowed**. `ConnectionService::checkConnectionPermission()` only ever returns Allowed or
Neutral — it **cannot deny**. So this layer strictly *adds* access on top of the permission checks
above; it never restricts.

Practical meaning: a Drupal user linked to a Contact can be granted view/update/delete/create over
the entity at the other end of a connection purely by virtue of the connection's Role. This is the
intended mechanism for e.g. letting an organization's primary contact manage that org. It is also a
**configuration surface to treat with care** — see the local security notes — because whoever can
create connections and choose the Role effectively chooses what access that delegation grants.

## Config that changes routing

`redhen.settings:redhen_admin_path` (default FALSE). When TRUE, the base RouteSubscriber and the
connection RouteSubscriber mark the canonical `/redhen` dashboard and
`entity.redhen_connection.canonical` as `_admin_route` (render in the admin theme). It does **not**
change access — access is always the permission checks above.
