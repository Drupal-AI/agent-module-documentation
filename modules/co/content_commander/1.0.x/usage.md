Content Commander creates and (optionally) resets Drupal content entities declaratively from PHP enums, resolving inter-entity dependencies automatically and running from the Dex console.

---

You declare each piece of content as a case of an enum that implements `Drupal\content_commander\ContentInterface` (optionally using `ContentTrait`), placed in a `src/ContentCommander/` directory of any custom module. Each case supplies a stable UUID (or returns `null` to let the module allocate and record one in the `content_commander.content_mapping` config), the entity class to build, and a `createContent()` body that fills in the entity fields. Inter-content dependencies are expressed with the `#[DependsOn(...)]` attribute on the enum case; a `Digilist\DependencyGraph` topologically sorts them so a referenced entity is always created first, and a circular dependency aborts the run. Content is generated by running the auto-registered Dex command (e.g. `dex content-commander:create-all`, or a per-enum command); passing `-d/--delete` first deletes any existing entity with the same UUID before recreating it.

Operationally this is a developer/CLI tool: it registers no routes, no permissions and no web-facing endpoints, so it has no anonymous or HTTP attack surface — it runs only through the Dex console (which itself requires shell access). The `-d` flag is destructive (it deletes matching entities), so the README warns against using it in production where it could wipe user edits. Stable UUIDs let the same logical content resolve to the same entity across environments; if you return `null` for the UUID the mapping is stored in `content_commander.content_mapping`, which you either export as config or add to the ignored-config list. Setup: `composer require drupal/content_commander` (pulls `drupal/dex_console`), enable it, then write your enums under a module's `src/ContentCommander/`.

---
- Define a content fixture as an enum implementing `ContentInterface`
- Generate all discovered content with `dex content-commander:create-all`
- Reset content before regenerating with the `-d/--delete` flag
- Seed a development site with known, repeatable content
- Create demo/marketing content that is identical across environments
- Give each fixture a fixed UUID so it maps to the same entity everywhere
- Let the module allocate and record a UUID via `content_commander.content_mapping`
- Express that one content item requires another with `#[DependsOn(...)]`
- Mark a dependency `optional` when its usage is conditional
- Have the module topologically order creation so references resolve first
- Detect and abort on circular content dependencies
- Reference a dependency entity inside `createContent()` via the ContentContext
- Build entities of any content entity type that supports UUIDs
- Use bundle classes as the entity class for a fixture
- Skip already-existing content on a non-deleting run (idempotent seeding)
- Look up a generated entity later via `ContentRepositoryInterface::getEntity()`
- Export `content_commander.content_mapping` to share UUID maps across sites
- Add the mapping config to ignored config when UUIDs may differ per environment
- Organize fixtures across multiple custom modules' `src/ContentCommander/` dirs
- Override the scanned namespaces via a site-level `services.yml` parameter
- Jump from console output to the defining enum in your IDE (phpstorm/vscode/…)
- Generate test content for automated or manual QA scenarios
