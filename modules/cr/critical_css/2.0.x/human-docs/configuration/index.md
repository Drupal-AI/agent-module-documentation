# Configuration

Critical CSS does nothing until you enable it and tell it where your critical CSS
files live. This page walks through the settings form and then explains the rules
the module uses to pick which file to inline on any given page.

## Open the settings form

1. Log in as a user with the **Administer site configuration** permission (an
   administrator by default).
2. Go to **Configuration → Development → Performance → Critical CSS**, or navigate
   directly to `/admin/config/development/performance/critical-css`.

Because the module ships no defaults, the configuration object does not actually
exist until you save this form once.

## The settings, field by field

### Enabled

The master on/off switch for the whole feature. Turn it off to disable critical
CSS without uninstalling the module. Rebuild the cache after changing this.

### Directory path

The directory that holds your critical CSS files, **relative to the active
theme**. It **must start with a `/`** and must **not** contain `..` (the form
validates this). For example, `/css/critical` resolves to
`themes/mytheme/css/critical/`. This is where you place the files you generated
externally — the module never creates them.

### Excluded IDs

A list of entity IDs to skip, **one per line**. Any entity listed here loads its
CSS normally (synchronously) instead of going through the critical CSS process.
Useful for a page you don't want touched.

### Enabled for logged-in users

Off by default. Critical CSS files are generated by emulating an **anonymous**
visitor, so authenticated users — whose pages may render differently — are
skipped unless you tick this. Only enable it if you're confident your logged-in
pages match the anonymous render closely enough.

### Preload non-critical CSS

Off by default. When on, the asynchronously loaded (non-critical) CSS is preloaded
at the highest priority. Reach for this only if you're fixing a Flash-Of-
Unstyled-Content (FOUC) problem — otherwise leave it off.

## Setting the values from Drush

You can set the two most common values from the command line instead of the form:

```bash
drush cset critical_css.settings enabled true
drush cset critical_css.settings dir_path '/css/critical'
```

## Which file gets inlined

For each request the module looks in your directory and inlines the **first
existing, non-empty** file it finds, trying these names in order from most to
least specific:

1. `{entity_id}.css` — e.g. `123.css` (the node or term ID on entity routes)
2. `path-{sanitized_path}.css` — internal path, e.g. `/node/123` →
   `path-node-123.css`
3. `{sanitized_path}.css` — e.g. `node-123.css`
4. `path-{sanitized_path_info}.css` — the request path, e.g. `path-my-article.css`
5. `{sanitized_path_info}.css` — e.g. `my-article.css`
6. `{bundle}.css` — the content type or vocabulary, e.g. `article.css`
7. `default-critical.css` — the catch-all fallback used when nothing else matches

Path names are "sanitized": the leading slash is stripped, characters outside
`a-z A-Z 0-9 / -` are removed, remaining slashes become dashes, and the empty
(front-page) path becomes `front`. So at minimum, create a `default-critical.css`
as your baseline and add more specific files where a particular page or content
type deserves tailored critical CSS.

> **Tip:** With Twig debug enabled, the module prints the list of candidate paths
> it tried as an HTML comment in the page source (look for `NONE MATCHED`) — handy
> for figuring out exactly what filename a given page expects.

## Interaction with CSS aggregation

When Drupal's CSS aggregation (**Configuration → Development → Performance**,
`css.preprocess`) is on, the inlined critical CSS is automatically run through
core's CSS optimizer, so you get minified output for free.

## Advanced: adding your own candidate paths

Developers can add or reorder the candidate file paths (for example to add a
per-language or per-role lookup) with
`hook_critical_css_file_paths_suggestion_alter()`. See the
[`agent/`](../agent/start.md) docs for the hook signature and an example.
