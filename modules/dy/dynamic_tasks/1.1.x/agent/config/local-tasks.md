# Managing dynamic local tasks

## Install & enable

```bash
composer require drupal/dynamic_tasks
drush en dynamic_tasks -y
```

No module dependencies, no external libraries, no submodules, no Drush commands. Core
`^9 || ^10 || ^11`.

## Permission & UI

- Permission: **`administer dynamic local tasks`** (`dynamic_tasks.permissions.yml`,
  `restrict access: true`) — grant only to trusted admins. It is the entity's `admin_permission`
  and gates every route below.
- Collection UI: **`/admin/structure/menu/dynamic-tasks`** (route
  `entity.local_task.collection`, the module's `configure` link; a "Local tasks" tab appears under
  *Structure → Menus* via `dynamic_tasks.links.task.yml`, and an "Add local task" action link via
  `dynamic_tasks.links.action.yml`).
- Entity routes (generated by core `AdminHtmlRouteProvider`, `src/Entity/LocalTask.php` `links`):
  add `…/dynamic-tasks/add`, edit `…/dynamic-tasks/manage/{local_task}`, delete
  `…/dynamic-tasks/manage/{local_task}/delete`.

## The `local_task` config entity

`src/Entity/LocalTask.php` — `@ConfigEntityType(id = "local_task")`, `config_prefix =
"dynamic_local_task"` (so instances are config objects `dynamic_tasks.dynamic_local_task.<id>`).
`entity_keys`: `id`, `label`, `weight`. Handlers: `LocalTaskListBuilder`, `LocalTaskForm` (add/
edit/default), core `EntityDeleteForm`, and `AdminHtmlRouteProvider`.

`config_export` / schema keys (`config/schema/dynamic_tasks.schema.yml`):

| Key | Type | Meaning |
|---|---|---|
| `id` | string | Machine name. |
| `label` | label | Tab title shown to users. |
| `route_name` | string | Route the tab **links to** (the destination page). |
| `route_parameters` | string | Newline-separated `key=value` pairs passed to that route. |
| `type` | string | `base_route` (primary tab) or `parent_id` (secondary tab). Controls which field below is used. |
| `base_route` | string | For a primary tab: the route on which this tab set appears. |
| `parent_id` | string | For a secondary tab: the parent primary-task plugin id it nests under. |
| `weight` | integer | Ordering among sibling tabs (form uses `#type weight`, delta 50). |

Note: `route_parameters` is stored as a single string, not a mapping; `LocalTask::getRouteParameters()`
splits it on newlines and each line on the first `=`.

## The form (`src/LocalTaskForm.php`)

- Fields: `label`, `id` (machine_name), `route_name`, `route_parameters` (textarea), `type`
  (radios: *Primary tab* = `base_route` / *Secondary tab* = `parent_id`), `base_route`,
  `parent_id`, `weight`. `base_route`/`parent_id` are shown/required conditionally via `#states`
  on the `type` radio.
- `route_name` and `base_route` use `#autocomplete_route_name => 'dynamic_tasks.autocomplete'`
  (search by route name or path).
- `validateForm()` enforces: the `route_name` route must exist (`getRoute()`); each
  `route_parameters` line must be `key=value` (normalized/re-imploded on save); and per `type`,
  either the `base_route` route must exist or the `parent_id` local task must exist. It also blanks
  the unused field (`parent_id` for a primary tab, `base_route` for a secondary tab).
- `save()` redirects back to the collection and shows a status message. Add/edit/delete are all
  POST forms with core CSRF/confirm handling.

## How tabs are generated (`src/Plugin/Derivative/DynamicLocalTasks.php`)

Wired as `dynamic_tasks.local_tasks` (deriver) in `dynamic_tasks.links.task.yml`.
`getDerivativeDefinitions()` loads every `local_task` entity and emits one
`menu.local_task` derivative each (`dynamic_tasks.<entity id>`) with `title`, `route_name`,
`route_parameters`, `weight`, plus `base_route` (primary) or `parent_id` (secondary) depending on
`type`. No custom plugin class or access override is set, so core's default local-task behavior
applies — including access-checking the linked route before rendering, so a tab never exposes a
page a user cannot already reach.

Cache: `LocalTask::getListCacheTagsToInvalidate()` adds the `local_task` cache tag so the tab menu
rebuilds when entities change (rebuild local tasks / `drush cr` if a new tab does not appear).

## Autocomplete route (`src/Controller/LocalTaskAutocompleteController.php`)

Route `dynamic_tasks.autocomplete` → `/dynamic-tasks/autocomplete`, `_format: json`,
`_permission: "administer dynamic local tasks"`. `autocomplete()` reads `q`, runs it through
`Xss::filter`, then queries the core `router` table (`name`, `path`, limit 10) with a
`LIKE %escapeLike(q)%` OR group across `name`/`path`, ordered by `path`, returning
`[{value: name, label: path}]`. Used only to help pick `route_name`/`base_route` in the form.

## Operating notes

- To find a route/base route, type part of the machine name or URL path in the autocomplete field.
- Primary vs secondary: pick *Primary tab* and a `base_route` to start a tab set on a page; pick
  *Secondary tab* and a `parent_id` (an existing primary local-task plugin id, e.g.
  `entity.node.canonical` style ids) to nest under an existing tab.
- Created tabs are configuration (`dynamic_tasks.dynamic_local_task.*`); export with
  `drush config:export` and deploy across environments like any config.
- The maintainers recommend defining local tasks in a module for normal cases; use this for
  special/no-code cases.
