Storage Entities provides a lightweight, bundleable content entity type (`storage`) for data that needs to be stored and fielded but not browsed at its own front-end URL — a cleaner alternative to making a content type just to hide it with Rabbit Hole.

---

The module defines a fieldable, revisionable, translatable content entity type **`storage`**
with configurable bundles called **storage types** (`storage_type`, a config entity). You
create storage types at `/admin/structure/storage_types` much like content types — each has
its own fields (via Field UI), a label, description, submission help text, default publish
status, revision defaults, and a **name pattern**. Storage entities are managed at
`/admin/content/storage` (a provided view) and created at `/storage/add`. Each entity has a
`name` base field (its label), author, timestamps and revisions; by default there is **no
canonical URL** — visiting `/storage/{id}` redirects to the edit form — unless the storage
type's `has_canonical` flag is enabled. The `name_pattern` storage-type setting lets you
auto-generate the name from tokens (e.g. `[storage:string-representation]`) on every save, so
you can hide the name field entirely. Permissions are granular per bundle
(`add/edit any/edit own/delete any/view published/...  <type> storage entities`) generated by
`StoragePermissions`, plus global admin permissions. The module ships publish/unpublish/save/delete
actions, a Views integration (base table `storage_field_data`, revision/status filters and
fields), token support (`hook_token_info`/`hook_tokens`), and an alter hook
`hook_storage_get_string_representation()` to customise an entity's string label. The optional
**rh_storage** submodule adds Rabbit Hole behaviour for storage entities. There is no single
settings page (`configure` is null); configuration lives in each storage-type config entity.

---

- Store structured data (e.g. API payloads, settings records, imported rows) without a content type.
- Replace a "content type hidden with Rabbit Hole" pattern with a purpose-built entity.
- Create multiple storage types (bundles), each with its own field set.
- Add fields to a storage type through the normal Field UI.
- Auto-generate each entity's name from a token pattern (`[storage:...]`).
- Hide the name field on the form when a name pattern supplies the value.
- Keep storage entities out of the front end (no canonical URL by default).
- Optionally enable a canonical URL for a storage type via `has_canonical`.
- Version storage data with revisions and revert/delete individual revisions.
- Expose or hide the "Create new revision" checkbox per storage type.
- Let editors write a revision log message when the revision log is exposed.
- Set whether new storage items are published by default per type.
- Manage all storage data from the `/admin/content/storage` overview view.
- Bulk publish/unpublish/delete storage entities with the shipped actions.
- Grant fine-grained per-bundle permissions (add/edit own/edit any/view/delete).
- Build custom views over storage data (base table `storage_field_data`).
- Reference storage entities from other entities via entity-reference fields.
- Use storage tokens in other text via the token integration.
- Customise an entity's displayed label with `hook_storage_get_string_representation()`.
- Translate storage entities (the entity type is translatable).
- Add Rabbit Hole behaviour to storage entities with the rh_storage submodule.
- Store editor/config data that should be fieldable but never publicly routable.
- Use storage types as a home for reusable structured fragments referenced across the site.
