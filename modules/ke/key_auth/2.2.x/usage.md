Key Authentication (`key_auth`) lets API clients authenticate as a Drupal user with a per-user API key sent as an HTTP header or query parameter, instead of a username/password or session cookie.

---

The module adds an `api_key` base field to the User entity and registers an authentication provider (`key_auth`, priority 200) that checks every request for a key via `KeyAuth::getKey()`. Where the key is looked for is configurable: a header and/or a query parameter, both named by the `param_name` setting (default `api-key`). If a key is present, `KeyAuth::getUserByKey()` looks up an *active* user whose `api_key` field matches, and the request authenticates as that user only if their roles carry the `use key authentication` permission — checked both to load-gate the auth and, separately, to decide whether a newly created user gets a key at all. Keys are generated by `KeyAuth::generateKey()`, which produces a random hex string truncated to the configured `key_length` (default 32) and guaranteed unique among users. If `auto_generate_keys` is enabled (the default), a key is assigned automatically when a user with the permission is created; otherwise (or to rotate/revoke), each user manages their own key at `/user/{user}/key-auth`, where they can generate a new key or delete the current one and see ready-made header/query examples. Site-wide behavior is configured at `/admin/config/services/key-auth`. A bundled page-cache request policy (`DisallowKeyAuthRequests`) prevents any request that carries a key from being served from the internal page cache, so authenticated responses are never leaked to anonymous cache hits.

---

- Authenticate a mobile app's REST API calls with a per-user key instead of a session cookie.
- Let a headless JavaScript/decoupled frontend call Drupal's JSON:API or REST resources as a specific user.
- Issue a machine-to-machine integration a dedicated Drupal user + API key instead of shared admin credentials.
- Send the key as an HTTP header (e.g. `api-key: <key>`) for server-to-server integrations that avoid query-string logging.
- Send the key as a URL query parameter (e.g. `?api-key=<key>`) for quick testing or clients that can't set custom headers.
- Restrict which detection method is accepted (header only, query only, or both) via `detection_methods`.
- Rename the parameter/header from the default `api-key` to something project-specific (e.g. `x-api-token`) via `param_name`.
- Automatically provision a new API-consuming user with a working key at creation time (`auto_generate_keys`).
- Require an explicit opt-in per role by gating key issuance and authentication behind `use key authentication`.
- Let end users self-serve: generate or rotate their own key from their account's Key authentication tab.
- Revoke a compromised key immediately by deleting it from the user's key-auth form (sets `api_key` to NULL).
- Rotate a service account's key on a schedule by calling `generateKey()` and saving it programmatically.
- Increase key entropy by raising `key_length` beyond the default 32 characters for higher-security integrations.
- Give an integration test suite disposable per-user keys instead of managing session logins.
- Avoid HTTP Basic Auth's username/password-in-every-request pattern for simple key-based access.
- Gate access to a specific REST/JSON:API endpoint to only requests bearing a valid key for a permitted user.
- Build a lightweight webhook receiver that authenticates inbound calls with a shared per-account key.
- Pair key_auth with core's REST module or JSON:API to secure a decoupled Drupal backend.
- Let admins manage another user's key via `/user/{uid}/key-auth` if they hold `administer users`.
- Prevent authenticated key-based responses from being cached and served to anonymous visitors via the bundled page-cache policy.
- Provide API consumers a copy-paste-ready header/query example generated straight from current settings.
- Disable automatic key generation site-wide and issue keys manually only to vetted integration accounts.
- Support both header- and query-based clients simultaneously during a migration between the two.
- Look up which Drupal user owns a given API key for auditing or support purposes via `getUserByKey()`.
- Combine key_auth with a permission-restricted role so only a "service account" role can hold usable keys.
- Swap basic_auth for key_auth on a site where storing/rotating passwords for machine accounts is undesirable.
