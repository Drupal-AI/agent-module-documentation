# Permissions

## Base module (`layout_builder_perms.permissions.yml`)

| Permission | `restrict access` | Gates |
|---|---|---|
| `access layout builder page` | (not set → FALSE) | The base gate for editing **per-entity layout overrides**. In the overridden `OverridesSectionStorage::access()` this is OR'd with the per-bundle "configure own editable …" permission — holding it alone grants override access to **any** overridable entity, with no ownership check. |

Dynamic permissions (via `permission_callbacks` → `LayoutBuilderPermissions::permissions`):

| Permission (per bundle) | Gates |
|---|---|
| `configure own editable {bundle} {entity_type} layout overrides` | Editing layout overrides on entities of that bundle **that the user owns** (AND-ed with core entity `update` access). One is generated for every display with `layout_builder.allow_custom = TRUE`. |

## Submodule permissions (enable the submodule to expose them)

All of these are plain (non-`restrict access`) permissions, generated by derivers; the label/
machine name pattern is shown — see each submodule doc for the deriver source.

- **Global** (`layout_builder_perms_global`): `create/edit/remove layout builder sections`,
  `create/config/remove/reorder layout builder blocks` — seven global operation permissions.
- **Per content type** (`layout_builder_perms_node`): `{action} {component}s on {bundle} nodes`,
  e.g. `add blocks on article nodes`, `remove sections on page nodes`.
- **Per layout type, sections** (`layout_builder_perms_layout_type`):
  `{action} layouts of type {layout_id}`.
- **Per entity type + bundle, sections** (`layout_builder_perms_layout_per_bundle`):
  `{action} {layout_id} layouts on {bundle} {entity_type} entities`.
- **Block operations per layout** (`layout_builder_perms_block_operations_per_layout`):
  `{action} {component}s in {layout_id} layouts`, e.g. `add blocks in layout_onecol layouts`.
- **Block types per layout** (`layout_builder_perms_block_types_per_layout`):
  `{action} {block_type} {component}s in {layout_id} layouts`.

## How they combine (crucial)

`AccessManager::access()` starts from `AccessResult::allowed()` and, for the current operation,
loads only the permission plugins whose context filters match (operation, layout id, entity
type, bundle, block type). Each matching plugin that `applies()` is AND-combined
(`$result->andIf($plugin->access())`). Consequences:

- **AND semantics:** if two submodules both contribute a matching plugin for the same operation
  (e.g. Global + Per-content-type), the user needs **both** permissions. Enabling more granular
  submodules makes access *stricter*, not looser.
- **Default allow:** if **no** plugin matches the operation/context, the result stays
  `allowed()`. For `overrides` section storage (which handles its own permission check) that
  default-allow is the final answer, so the only remaining gate is the base
  `access layout builder page`. For `defaults` (template) layouts the global
  core `configure any layout` permission is additionally AND-ed, so those stay locked down.

Grant granular permissions from `/admin/people/permissions` after enabling the submodule; they
are ordinary role permissions and can be exported in config.
