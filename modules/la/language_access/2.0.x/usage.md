Language Access gates access to each configured site language behind a per-language permission (`access language <langcode>`), so roles that lack a language's permission are blocked from its pages and never see it in switchers, hreflang tags, or sitemaps.

---

The module defines one dynamic permission per configured language, named `access language <langcode>` (e.g. `access language en`, `access language fr`), generated by a permission callback from the language manager. A `kernel.request` event subscriber throws `AccessDeniedHttpException` (HTTP 403) on the main request whenever the current user lacks the permission for the current request's language, except on `/user/`, the public files path, and `/s3/` paths (and never on CLI/Drush). Beyond hard access, it prunes the language everywhere it would leak: `hook_language_switch_links_alter()` removes inaccessible switcher links, `hook_page_attachments_alter()` strips `hreflang` alternate tags, `hook_simple_sitemap_links_alter()` drops sitemap entries and alternates for the anonymous user, and it limits the language options offered on the user form's *preferred language* field and on `language_select` widgets. It also swaps core's browser language-negotiation plugin and the `config_pages` language context plugin for access-aware variants, and rewrites the content-translation overview controller (with a TMGMT-aware variant when `tmgmt_content` is on). On install it grants `access language <default>` to the anonymous and authenticated roles so the default language keeps working. There is no settings form and no config — everything is driven by the permissions page (`configure` is `null`).

---

- Restrict a half-translated language so only editors (with `access language de`) can browse the German site while it is being prepared.
- Grant `access language fr` to a specific role so only French-speaking staff can reach French pages.
- Return HTTP 403 to anonymous visitors who try to open a language they are not permitted to see.
- Hide unavailable languages from the language switcher block so users only see languages they can access.
- Remove `hreflang` alternate `<link>` tags for restricted languages to avoid exposing them to search engines.
- Drop restricted-language URLs (and their alternates) from a Simple Sitemap XML sitemap.
- Limit the *Preferred language* options on the user account form to languages the account may access.
- Limit the options of a `language_select` field widget to accessible languages for the current user.
- Soft-launch a new translation to a review team before making it public.
- Keep the default language open to everyone (granted automatically on install) while locking down the rest.
- Provide per-role editorial access to translations in a workflow where translators own specific languages.
- Prevent browser Accept-Language negotiation from routing a user into a language they cannot access.
- Restrict language-specific config pages (config_pages) to users with the matching language permission.
- Filter the content-translation overview so editors only act on languages they are allowed to.
- Combine with content_translation to give per-language content editing boundaries.
- Allow anonymous users to see only the primary language while authenticated staff see additional ones.
- Stage a multilingual site launch language-by-language by flipping one permission at a time.
- Exempt user account routes and file downloads from language blocking so login and assets always work.
- Enforce language boundaries site-wide without writing custom access checks.
- Use permissions export/import to deploy per-language access rules across environments.
- Give a translation agency (via TMGMT) a scoped overview limited to their languages.
- Keep Drush and cron unaffected by language access (the check is skipped on CLI).
- Grant an "all languages" super-role by assigning every `access language *` permission.
- Quietly retire a language from public view by revoking its permission from anonymous instead of deleting content.
