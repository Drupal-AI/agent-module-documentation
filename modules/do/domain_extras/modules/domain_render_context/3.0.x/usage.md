A developer-API service that runs a callback as if the request had come from a chosen domain, so out-of-band output (an email, a PDF, a queue item) gets that domain's links, per-domain configuration, path prefixes and theme instead of those of the request doing the work.

---

Domain Render Context is a code-only module (no routes, UI, permissions or config) providing one service, `domain_render_context.renderer` (class `Drupal\domain_render_context\DomainRenderContext`, interface `Drupal\domain_render_context\DomainRenderContextInterface`, also autowired by its interface). It solves the case where the process advancing a piece of work is not the domain the work belongs to — an operator validating a public-site order from the back office, cron releasing a booking with no active domain, a queue worker mailing a customer hours later — so rendering would otherwise inherit the wrong host, site name and per-domain overrides. `inDomain(DomainInterface|string $domain, callable $callback): mixed` runs `$callback` under the target domain and always restores on the way out (a `finally`); `enter(DomainInterface|string $domain): \Closure` is the lower-level form for work that does not fit one callback and returns a restore closure the caller must invoke (idempotent, and nesting restores correctly when closures run in reverse order). It switches exactly three things: the `domain.negotiation_context` (per-domain config overrides, domain path prefix, that domain's language negotiation), the `router.request_context` scheme/host/port (the host of absolute URLs), and the active theme read from the render domain's own `system.theme` config. It does not change interface language, session or current user, and does not push a request onto the stack. Passing an unknown machine name is logged and the current context kept (a deleted domain never fatals a notification). Meant for outbound rendering only — never during page routing/render for the browser. Depends only on `domain:domain`.

---

- Render an email so its links, site name and config match the domain an order/booking belongs to.
- Build a PDF or other attachment under a specific domain's context.
- Fix wrong absolute URLs generated by cron with no active domain.
- Render a queue worker's output in the domain the queued item belongs to.
- Wrap any callback with `inDomain($domain, $callback)` and get the return value back.
- Pass a domain machine name (string) or a loaded `DomainInterface` as the target.
- Use `enter($domain)` for work spanning multiple statements, restoring in a `finally`.
- Switch context for the whole of a queue worker's `processItem()` via `enter()`.
- Nest context switches, restoring the returned closures in reverse order.
- Get the render domain's per-domain configuration overrides (site name, site mail, etc.) applied to reads inside the callback.
- Make outbound routed URLs (`Url::fromRoute()`, `$entity->toUrl()`, `[site:url]`) point at the target domain's host.
- Have rendered output pick up the render domain's own theme (templates, assets, logo).
- Let a mail theme applied inside the callback still win, since it switches later.
- Render correctly from a CLI/cron context that has not negotiated any domain yet.
- Tolerate a deleted/unknown target domain: it is logged and the current context is kept.
- Inject the service by its interface (`DomainRenderContextInterface`) via autowiring.
- Handle non-standard ports and per-domain http/https schemes in generated URLs.
- Keep any subdirectory Drupal is installed in while swapping only the origin.
- Prefer Domain core's per-URL `['domain' => $domain]` option for a single link that needs no full context switch.
